## 2. 源生态全景：四层订阅结构

```
多仓（storeHouse，"仓库的仓库"）
  └── 单仓（TVBox 配置 JSON，spider + sites + lives + parses + rules + ...）
        ├── 点播站点 sites[]（type 0/1 = CMS 直连；type 3 = 蜘蛛）
        │     └── 蜘蛛子生态：csp_ jar / drpy js / lf_js / py / hipy t4 ...
        └── 直播 lives[] → m3u / txt / json 频道表 + EPG 模板
```

五款竞品（TVBox/影视仓/影迷/喵影视/可视TV）的源规则同源（TVBox 生态），影视仓多仓、可视TV 仓库均为该结构的变体。**结论：兼容 TVBox 单仓规范 = 覆盖市面主流订阅源**；此外 LibreTV/MoonTV（Web 端）的苹果CMS源声明格式简单，作为附加导入器实现成本极低。

## 3. TVBox 单仓配置规范（核心）

### 3.1 顶层字段

✔ 源码 + ✔ 实测（顶层字段清单来自真实配置统计，非完整官方列表——该规范没有官方文档，字段以实现为准）：

| 字段 | 类型 | 语义 | 证据 |
|---|---|---|---|

### 3.3 JS 蜘蛛的声明方式（实测定论）

gaotianliuyun/gao `js.json`（298 个 type3 站点）✔ 实测：

```json
{ "key": "drpy_js_豆瓣", "name": "豆瓣", "type": 3,
  "api": "./lib/drpy2.min.js", "ext": "./js/drpy.js" }
{ "key": "lf_js_search", "name": "lf搜索", "type": 3,
  "api": "./lib/lf_search3_min.js", "ext": "18+" }
```

规律：**`api` = JS 运行时引擎文件**（drpy2.min.js 或其他自定义运行时），**`ext` = 该源的源码文件路径或参数**。壳把运行时 JS 装入 QuickJS，再把 ext 源装载为站点。FongMi/TV 的分发逻辑 ✔ 源码（`BaseLoader.java`）：

```java
if (isPy(api)) return pyLoader.getSpider(...);      // api 含 ".py"
else if (isJs(api)) return jsLoader.getSpider(...); // api 含 ".js"
else if (isCsp(api)) return jarLoader.getSpider(...); // api 以 "csp_" 开头
```

`csp_X` → `com.github.catvod.spider.X` 类 ✔ 源码（FongMi `JarLoader`）。

### 4.1 csp_ jar 爬虫（Java/dex）

**Spider 基类契约** ✔ 源码（bizhangjie/CatVodSpider `Spider.java`）：

## 5. 苹果CMS（MacCMS）API 规范

### 5.1 请求参数 ✔ 源码（Provide.php）+ ✔ 实测

接口基地址：`http(s)://域名/api.php/provide/vod/`（路径式参数 `/at/xml/`、`/from/xxx/` 与查询式等价）。除 vod 外还有 `art/actor/role/website` 同构接口（影视聚合用不到）。

| 参数 | 含义 | 备注 |
|---|---|---|
| `ac` | `list`（缺省）/`detail`/`videolist`（=detail 别名） | list 为精简字段，detail 为全字段 |
| `at` | 缺省 JSON；`at=xml` 输出 XML | ✔ 实测两种都验证 |
| `wd` | 搜索词（like 模糊） | ✔ 实测 bfzy 命中 8854；**suoni 搜索响应缺 total 字段 → 引擎须容忍** |
| `t` | 分类 type_id | |
| `pg` | 页码（缺省 1） | **`pagecount=0` 时必须停翻页**（死循环坑） |
| `h` | 最近 N 小时更新 | |
| `ids` | 指定影片 id（逗号分隔） | 部分站 ac=detail 不带 ids 不给 play_url |
| `pagesize` | 每页数 | 源码上限 100，站点常自定 |
| `isend`/`year`/`from`/`sort_direction` | 完结/年份(支持区间)/播放组过滤/排序 | |
| `not`/`lang` | 排除/语言 | 未证实为官方参数（变体站私有） |
| `appid`/`sign` | 鉴权 | 私有实现（未证实为官方规范） |

### 5.2 JSON 返回 ✔ 实测逐字段核对（暴風 bfzyapi、索尼 suoniapi 全通过）

- `ac=list` 的 `list[]` 实测字段（与源码"精简查询"完全一致）：`vod_id, vod_name, type_id, type_name, vod_en, vod_time, vod_remarks, vod_play_from`；外层 `code(1)/msg/page/pagecount/limit/total/class[]`（class 含 `type_id/type_pid/type_name`；**ac=detail 不返回 class**）。
- `ac=detail`：实测返回 **83 个字段**（vod_pic/area/lang/year/serial/actor/director/content/state/class/score/hits/tag/play_url/down_* 等），**站点裁剪字段不可假设齐全**。
- `vod_time` 是 `Y-m-d H:i:s` 字符串而非时间戳；`vod_remarks` 常为"更新至xx集/HD/蓝光"（做角标）；`vod_play_from` 在 list 模式下 `$$$` 被替换为 `,`（源码行为）。

### 5.4 播放地址解析约定 ✔ 源码+实测

- `vod_play_from`：多线路 `$$$` 分隔（如 `bfzym3u8`；多线路 `ffm3u8$$$zuidam3u8`）
- `vod_play_url`：与 from 一一对应；线路内 `#` 分集；集内 `集名$地址`；换行符按 `#` 处理（源码行为）
- 地址形态：`.m3u8`（主流）/`.mp4`/网页地址（需解析——**星映不做网页解析**，见 05 合规节）
- ✔ 实测端到端：bfzy 详情返回的 m3u8 直链 HTTP 200（`application/vnd.apple.mpegurl`），播放链路成立

### 5.5 同构 CMS 变体

海洋CMS（XML-only，接口同构）、飞飞CMS（老式 `api.php?ac=list|detail`）——资源站普遍"同时支持苹果/海洋/飞飞采集"，一个解析器 + 少量变体分支即可覆盖；AppYsV2 的 `{api}/api.php/v1.vod` 归入 CMS JSON 变体。

### 6.1 多仓（storeHouse）✔ 实测实例（c120487/00）

```json

```

"txt 仓"= 逐行列出单仓地址的纯文本。影视仓/可视TV 的"仓库"概念同构。

### 6.2 直播源三格式 ✔ 实测

**TXT**（qist tvlive.txt 实测通过）：

```
黑龙江移动,#genre#
CCTV1,http://[2409:8087:...]/PLTV/.../1.m3u8?icpid=...
CCTV2,http://...#http://...     ← 同名多地址 # 分隔轮换
```

**M3U**（fanmingming/live 实测通过，注意 `catchup` 回看扩展与自定义属性）：

```
#EXTM3U x-tvg-url="https://live.fanmingming.cn/e.xml" catchup="append" catchup-source="?playseek=${(b)yyyyMMddHHmmss}-${(e)yyyyMMddHHmmss}"
#EXTINF:-1 tvg-name="CCTV1" tvg-logo="https://.../CCTV1.png" group-title="央视频道",CCTV-1综合
http://.../1.m3u8
```

**EPG** ✔ 实测：`e.xml?ch={频道名}&date={YYYY-MM-DD}` 返回标准 XMLTV（`<tv><channel id><display-name>` + `<programme>`）。配置中 `lives[].epg` 模板用 `{name}`/`{date}` 占位。

**JSON 直播**：`groups[].channel[]` 结构（社区文档描述，未证实为通用规范——低优先级支持）。

### 6.3 Web 端聚合项目的源声明（附加兼容，成本低）

## 7. 生态工程观察（影响引擎设计的现实问题）

1. **配置 JSON 前允许注释/杂质**：实测 2 个存活配置在 JSON 前有 `//` 注释行（liucn、pastebin1），解析前必须剥离 BOM、注释行、空白与尾逗号容错。
2. **入口型域名**：`肥猫.live`、`bp.tvbox.cam`、菜妮丝等对 curl 返回 HTML 落地页（200），真实接口可能按 UA/路径分流或在页面内跳转——引擎需 HTML 落地页识别 + 从页面提取真实接口 URL 的兜底逻辑（常见做法是页面 JS/正文给出新地址）。
3. **镜像前缀高死亡率**：`mirror.ghproxy.com`、`github.moeyy.xyz` 实测全部 000；同一文件直连 raw.githubusercontent（经代理）全部可用。引擎不应缓存/依赖特定镜像前缀，应把镜像视为用户侧代理问题。
4. **站点裁剪字段**：detail 83 字段 ≠ 全站都有；`total` 可能缺失；`pagecount` 可能为 0。
5. **jar 覆盖陷阱**（社区已知）：合并多配置时全局 `spider` 被覆盖会使无站点级 jar 的 type3 站点失效——星映按"每个站点固化其解析器来源"设计可根治。
6. **type4（hipy t4）**：存在但细节未证实；P2 抓包逆向后再支持。
